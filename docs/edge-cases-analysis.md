# 경계 상황 및 오류 가능성 분석

대출 계산에서 정상 입력만 처리하는 것보다 **잘못된 값이 들어왔을 때 틀린 금융 결과를 만들지 않는 것**을 중요하게 봅니다.

## 1. 소수점 계산 오차

### 발생 가능 상황
- 수백 개월의 장기 상환에서 반복 계산
- 원금균등 방식에서 월별 이자를 누적하는 경우

### 현재 방향
- 기존 TypeScript 계산은 `Big.js` 사용
- Java/Spring 백엔드는 `BigDecimal` 사용
- 최종 금액의 반올림 규칙을 명시적으로 관리

### 확인할 점
금융 도메인에서는 단순히 오차가 작다는 이유로 무시하기보다 **어느 단위에서 어떤 반올림 규칙을 사용할지**를 명확하게 정해야 합니다.

---

## 2. 금리 경계값

### 0% 금리

무이자 상품이나 우대 적용 결과 금리가 0%가 될 수 있습니다.

```typescript
if (monthlyRate.eq(0)) {
  return principal.div(months);
}
```

확인할 항목:
- 0으로 나누는 계산이 없는가
- 월 절감액이 0일 때 손익분기점 계산을 시도하지 않는가
- 중도상환수수료만 발생하는 상황을 올바르게 설명하는가

### 음수 금리

사용자 입력이나 우대금리 계산 오류로 음수가 만들어질 수 있습니다. 단순히 0으로 바꿔 계산하기보다 입력값 검증 단계에서 잘못된 값인지 확인하는 것이 안전합니다.

### 비현실적으로 높은 금리

금리 범위를 벗어난 값은 API와 DB 양쪽에서 차단합니다. 애플리케이션 검증만 믿지 않고 DB CHECK 제약조건을 마지막 방어선으로 둡니다.

---

## 3. 상환 기간 경계값

### 잔여 기간이 0 이하

```typescript
if (currentDebt.remainingMonths <= 0) {
  throw new Error('잔여 상환 기간이 없습니다.');
}
```

0으로 나누는 계산과 의미 없는 시뮬레이션을 막아야 합니다.

### 잔여 기간이 전체 기간보다 큼

사용자 입력 오류이므로 계산 전에 거절합니다.

```typescript
if (currentDebt.remainingMonths > currentDebt.totalMonths) {
  throw new Error('잔여 기간이 전체 기간보다 클 수 없습니다.');
}
```

---

## 4. 중도상환수수료

### 수수료가 없는 상품

수수료 면제 기간이 0인 경우 처음부터 수수료가 없는 상품으로 해석할 수 있습니다. DB 기본값과 실제 상품 정책을 구분해야 합니다.

### 비정상적으로 높은 수수료율

수집 오류나 입력 실수를 막기 위해 범위를 검증합니다. 단순 경고만 할지 요청을 거절할지는 실제 금융상품 정책에 맞춰 결정해야 합니다.

---

## 5. 손익분기점 계산

### 월 절감액이 0 이하

신규 대출이 더 비싸거나 총비용이 줄어들지 않는 경우 손익분기점을 계산하면 의미가 없습니다.

```text
월 절감액 <= 0
→ 손익분기점 없음
→ 대환 이점 없음으로 명시
```

### 손익분기점이 잔여 기간보다 긴 경우

비용을 회수하기 전에 대출이 끝나므로 현재 대출 유지가 더 합리적일 수 있습니다. 결과에는 단순 추천값뿐 아니라 이유를 함께 제공하는 방향이 좋습니다.

예:

```text
손익분기점 48개월 > 잔여 기간 36개월
→ 대환 비용을 회수하기 어려움
```

## 6. 수수료 면제일까지 기다릴지 여부

기존의 단순한 “3개월 이내면 대기” 규칙은 임의적일 수 있습니다.

더 좋은 기준은 두 선택의 실제 비용을 비교하는 것입니다.

```text
지금 대환했을 때의 순절감액
vs
수수료 면제일까지 기다린 뒤 대환했을 때의 순절감액
```

```typescript
const savingsIfWait = calculateSavingsIfWait(monthsUntilWaiver);
const savingsIfNow = netSavings;
```

임의의 기간 기준보다 실제 금액 비교를 우선합니다.

---

## 7. 여러 상품 중 선택

현재는 순절감액을 주요 기준으로 비교합니다.

추가 기준이 필요하다면 손익분기점이나 월 절감액을 함께 보여줄 수 있습니다. 다만 근거 없는 가중치 점수를 임의로 넣기보다 사용자에게 각 지표를 직접 제공하는 편이 더 설명 가능할 수 있습니다.

---

## 8. 큰 금액과 자료형

`Big.js`나 `BigDecimal`을 사용하더라도 마지막에 JavaScript `number`로 바꾸는 순간 표현 범위의 영향을 받을 수 있습니다.

따라서 큰 금액을 다룰 때는:
- 변환 시점 최소화
- 문자열 반환 검토
- 허용 가능한 원금 범위 검증

을 함께 고려합니다.

---

## 9. 누락된 값

외부 데이터 수집 실패로 일부 필드가 비어 있을 수 있습니다. 무조건 기본값으로 채우면 실제 의미와 다른 데이터를 만들 수 있으므로 필수값은 적재 전에 검사하고, 불완전한 상품은 별도로 처리하는 것이 안전합니다.

---

## 10. 계산 비용

매 상품마다 전체 월별 상환표를 만들면 상품 수와 기간이 커질수록 반복 계산량이 증가합니다.

상세 월별 표가 필요하지 않은 요청에서는 총 이자나 총비용만 계산하는 경로를 분리할 수 있습니다.

```text
상세 상환표 필요
→ 월별 스케줄 생성

총비용만 필요
→ 필요한 값만 계산
```

성능 최적화는 실제 병목을 측정한 뒤 적용합니다.

## 11. 보안과 입력 검증

### DB 접근

Supabase RLS와 서버 권한 설정을 확인해야 합니다. 애플리케이션 입력 검증과 DB 접근 권한은 별개의 문제입니다.

### 화면 출력

사용자나 외부 데이터에서 들어온 문자열은 화면에 출력할 때 안전하게 처리해야 합니다. 프레임워크 기본 보호를 사용하더라도 직접 HTML을 삽입하는 경로가 없는지 확인합니다.
