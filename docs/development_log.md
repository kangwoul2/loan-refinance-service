# 개발 기록

## 프로젝트 목적

대환대출에서 단순 금리 차이가 아니라 **중도상환수수료, 남은 기간, 상환 방식, 대환 비용을 포함한 총비용**을 비교하기 위해 시작했습니다.

프로젝트는 다음 순서로 확장했습니다.

```text
금융 계산
  ↓
외부 상품 데이터 수집
  ↓
입력값과 DB 무결성 강화
  ↓
Java/Spring 백엔드 추가
  ↓
동시 갱신과 재시도 중복 처리
  ↓
캐시와 성능 검증
```

---

## 1단계. 문제 정의

핵심 질문은 다음과 같습니다.

> 중도상환수수료와 대환 비용을 내더라도 새로운 대출로 갈아타는 것이 실제 총비용 기준으로 유리한가?

따라서 비교 항목을 금리 하나가 아니라 다음처럼 정의했습니다.

```text
현재 대출의 남은 총비용
vs
새 대출의 총비용 + 중도상환수수료 + 이전 비용
```

---

## 2단계. 금융 계산 구조

### 소수 정밀 연산

JavaScript 기본 숫자형의 부동소수점 오차를 줄이기 위해 기존 TypeScript 계산에는 `Big.js`를 사용했습니다. 이후 Java/Spring 백엔드에서는 같은 이유로 `BigDecimal`을 사용합니다.

### 상환 방식 분리

원리금균등과 원금균등의 계산 정책을 별도 계산기로 분리했습니다.

```text
시뮬레이션 서비스
  ↓
상환 방식 선택
  ├─ 원리금균등 계산기
  └─ 원금균등 계산기
```

핵심 서비스가 계산식 자체까지 모두 가지지 않도록 책임을 나눈 구조입니다.

### 주요 계산

원리금균등:

```text
월 상환액 = P × [r × (1+r)^n] / [(1+r)^n - 1]
```

원금균등:

```text
월 원금 = P / n
월 이자 = 남은 원금 × 월 이자율
```

손익분기점:

```text
손익분기점 = 대환 비용 / 월 절감액
```

실제 금융상품의 수수료 정책은 상품별로 다를 수 있으므로 현재 계산 규칙을 모든 금융기관의 실제 정책으로 일반화하지 않습니다.

## 3단계. 금융상품 데이터 수집

사용자 웹 요청 안에서 외부 사이트를 직접 수집하지 않고 Python 데이터 수집 작업으로 분리했습니다.

```text
외부 금융상품 페이지
  ↓
Python 수집
  ↓
필수값 / 범위 / 중복 검사
  ↓
DB 적재
  ↓
웹 서비스 조회
```

분리한 이유는 외부 사이트의 지연과 실패가 사용자 API 응답시간에 직접 영향을 주지 않게 하기 위해서입니다.

---

## 4단계. 입력값과 DB 무결성

애플리케이션 입력 검사만으로 데이터 무결성을 끝내지 않았습니다.

- 필수값 검사
- 금리·기간·금액 범위 검사
- 상품 중복 검사
- DB CHECK 제약조건
- 상품 식별 조합 유일성 제약조건

DB를 마지막 무결성 경계로 두는 방향입니다.

---

## 5단계. Java/Spring 백엔드 확장

기존 화면과 데이터 수집 코드는 보존하면서 Spring Boot 백엔드를 추가했습니다.

추가로 다룬 문제:

1. 금융 계산을 `BigDecimal`로 처리
2. 상품 저장을 PostgreSQL/JPA로 관리
3. DB 변경 이력을 Flyway로 관리
4. 여러 DB 상태를 트랜잭션으로 묶기
5. 동시 상품 갱신에서 갱신 손실 방지
6. 재시도 요청의 중복 저장 방지
7. 상품 조회 캐시 실험

---

## 6단계. 동시 갱신

같은 상품을 동시에 수정하면 한 요청의 변경이 사라질 수 있습니다.

```text
A가 버전 3 조회
B가 버전 3 조회
A가 수정 성공 → 버전 4
B가 버전 3 기준으로 수정 시도
→ 오래된 요청으로 판단
→ HTTP 409
```

JPA `@Version`을 이용한 낙관적 락을 적용했습니다.

선택 기준은 **충돌이 드물다는 가정**입니다. 충돌이 매우 잦고 순차 실행이 중요하다면 비관적 락을 검토할 수 있습니다.

---

## 7단계. 재시도 안전성

데이터 수집기가 요청 처리 결과를 받기 전에 네트워크 오류가 발생하면 같은 요청을 다시 보낼 수 있습니다.

```text
서버 저장 성공
  ↓
응답 전달 실패
  ↓
클라이언트가 성공 여부를 모름
  ↓
같은 요청 재시도
```

이를 위해:

- 같은 논리적 요청은 `Idempotency-Key`로 식별
- 같은 금융상품은 DB 유일성 제약조건으로 최종 차단

하도록 역할을 나눴습니다.

---

## 8단계. 캐시

상품 목록처럼 읽기가 많은 기능에 Spring Cache를 적용했습니다.

```text
서버 한 대
→ 프로세스 내부 캐시

서버 여러 대
→ 로컬 캐시 상태가 달라질 수 있음
→ Redis 공유 캐시 검토
```

Redis가 항상 더 빠르다고 가정하지 않습니다. Redis는 네트워크 통신 비용이 있지만 여러 서버가 같은 캐시 상태를 공유할 수 있다는 장점이 있습니다.

비교 지표:
- p50 / p95 지연시간
- DB 조회 횟수
- 캐시가 비어 있는 첫 요청 비용
- 캐시 무효화 이후 동작

## 주요 경계 상황

- 잔여 기간이 0 이하
- 잔여 기간이 전체 기간보다 큼
- 금리가 음수이거나 허용 범위를 초과
- 월 절감액이 0 이하
- 손익분기점이 잔여 기간보다 김
- 필수 금융상품 정보 누락
- 매우 큰 금액

상세 내용은 `docs/edge-cases-analysis.md`에 정리합니다.
