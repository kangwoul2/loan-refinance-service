# 백엔드 면접 가이드

모든 답변은 **문제 → 원인 → 대안 → 선택 → 단점 → 검증** 순서로 설명합니다. 기술 이름을 먼저 말하기보다 어떤 문제를 해결하기 위해 선택했는지를 먼저 설명합니다.

## Q1. 왜 금융 계산에 `BigDecimal`을 사용했나요?

금융 계산은 금리, 이자, 수수료를 반복해서 계산하기 때문에 작은 소수점 오차도 누적될 수 있습니다. `double`을 그대로 사용하는 방법이나 최소 화폐 단위 정수로 바꾸는 방법도 있지만, 금리처럼 소수 값을 계속 다뤄야 하므로 Java 백엔드에서는 `BigDecimal`을 사용했습니다. 핵심은 계산 속도보다 결과의 정확성과 반올림 규칙을 명확하게 관리하는 것입니다.

## Q2. 왜 상환 방식별 계산기를 분리했나요?

원리금균등과 원금균등은 계산식이 다르고 이후 다른 상환 방식이 추가될 수 있습니다. 하나의 서비스에서 조건문을 계속 늘리는 대신 계산 정책을 별도 객체로 분리해 서비스 흐름과 계산식을 나눴습니다. 새로운 상환 방식이 추가되어도 기존 서비스 흐름의 변경을 줄일 수 있습니다.

## Q3. 데이터 수집을 왜 사용자 요청 안에서 바로 하지 않았나요?

사용자 요청은 짧고 예측 가능한 응답시간이 중요하지만 외부 사이트 수집은 네트워크 지연, 실패, 재시도가 발생할 수 있습니다. 실시간 요청 안에서 수집하면 외부 사이트의 지연이 그대로 사용자 지연시간으로 이어집니다. 그래서 데이터 수집과 정제를 별도 Python 작업으로 분리하고, 웹 서비스는 이미 저장된 데이터를 조회하도록 구성했습니다.

## Q4. 왜 Kafka나 별도 대기열을 처음부터 넣지 않았나요?

현재 규모에서는 메시지 브로커가 해결하는 문제보다 운영 복잡도가 더 큽니다. 수집 작업이 많아져 재시도, 일정 실행, 작업 처리자 수평 확장이 실제로 필요해지는 시점에 대기열을 도입하는 편이 적절합니다. 기술을 먼저 넣지 않고 실제 문제가 확인된 뒤 확장하는 방향을 선택했습니다.

## Q5. DB에 유일성 제약조건과 CHECK 제약조건을 둔 이유는 무엇인가요?

애플리케이션에서 입력값을 검사해도 데이터 수집기, 배치 작업, 직접 SQL 등 다른 경로로 잘못된 값이 들어올 수 있습니다. 그래서 DB를 마지막 무결성 경계로 두고 금리와 기간 범위에는 CHECK 제약조건, 상품 식별 조합에는 유일성 제약조건을 적용했습니다.

## Q6. 같은 상품을 두 번 수집하면 어떻게 되나요?

`(bank_name, product_name)` 유일성 제약조건이 같은 상품의 중복 저장을 최종적으로 막습니다. 같은 HTTP 적재 요청이 네트워크 문제로 다시 들어오는 경우에는 `Idempotency-Key`를 저장해 같은 논리적 요청의 재시도를 식별합니다. 즉 유일성 제약조건은 같은 상품, 멱등성 키는 같은 요청을 보호합니다.

## Q7. 트랜잭션은 어디에 사용하나요?

여러 DB 상태가 하나의 논리적 작업으로 함께 변경되어야 할 때 사용합니다. 예를 들어 상품 저장과 멱등성 처리 기록은 둘 중 하나만 성공하면 다음 재시도에서 상태가 어긋날 수 있으므로 하나의 트랜잭션으로 묶습니다. 반면 외부 사이트 요청 전체를 트랜잭션 안에서 기다리면 DB 연결과 락을 오래 점유하므로 외부 I/O와 DB 트랜잭션은 분리합니다.

## Q8. 낙관적 락과 비관적 락은 어떤 기준으로 선택하나요?

충돌 빈도와 충돌 시 비용을 기준으로 선택합니다. 충돌이 드물면 버전 값을 이용한 낙관적 락으로 일단 갱신을 시도하고 충돌이 발생한 경우에만 다시 처리하는 편이 효율적입니다. 동일한 행에 높은 빈도로 수정이 몰리고 반드시 순차 실행해야 한다면 비관적 락을 검토합니다.

## Q9. Redis 분산 락은 언제 필요한가요?

여러 서버가 DB 행과 직접 연결되지 않은 같은 외부 작업을 동시에 실행하지 않도록 조정해야 할 때 후보가 됩니다. 예를 들어 여러 데이터 수집 작업자가 같은 수집 작업을 중복 수행하지 않도록 막아야 하는 경우입니다. 하지만 DB 유일성 제약조건이나 멱등성으로 해결할 수 있다면 더 단순한 방법을 먼저 사용합니다.

## Q10. 이 프로젝트에서 가장 중요하게 본 백엔드 문제는 무엇인가요?

우선순위를 **계산 정확성 → 데이터 정합성 → 동시성 → 재시도 안전성 → 성능**으로 잡았습니다. 금융 계산은 `BigDecimal`, 동시 갱신은 낙관적 락, 재시도 중복은 멱등성 키와 DB 유일성 제약조건으로 각각 문제에 맞는 수단을 사용했습니다.

## 30초 답변

> 대환대출 서비스에서는 먼저 금액 계산이 틀리지 않도록 `BigDecimal`을 사용했습니다. 같은 상품을 동시에 수정할 때는 갱신 손실이 생길 수 있어 JPA `@Version`으로 낙관적 락을 적용하고 오래된 버전의 수정 요청은 409로 반환했습니다. 데이터 수집기가 네트워크 오류로 같은 요청을 재시도할 수 있어 멱등성 키와 DB 유일성 제약조건으로 중복 저장을 막았습니다. 외부 사이트 수집은 DB 트랜잭션 밖에서 수행해 DB 자원을 오래 점유하지 않도록 했습니다. 조회 캐시는 Redis가 무조건 빠르다고 가정하지 않고 프로세스 내부 캐시와 공유 캐시의 비용을 직접 비교하도록 구성했습니다.
