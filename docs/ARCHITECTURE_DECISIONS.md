# 설계 결정 기록

기능 목록보다 **왜 이 구조를 선택했는지**를 설명하기 위한 문서입니다.

## 1. 금융 계산에 소수 정밀 연산 사용

### 문제
JavaScript `Number`는 IEEE-754 부동소수점 표현을 사용하므로 반복적인 금융 계산에서 작은 오차가 생길 수 있습니다.

### 검토한 대안
1. `Number` 그대로 사용
2. 모든 값을 최소 화폐 단위 정수로 변환
3. 소수 정밀 연산 라이브러리 사용

### 선택
기존 TypeScript 계산에서는 `Big.js`, Java 백엔드에서는 `BigDecimal`을 사용합니다.

### 단점
- 장점: 금리·수수료·누적 상환액의 계산 규칙을 명확하게 관리할 수 있음
- 단점: 기본 숫자형보다 사용법이 복잡하고 반올림 규칙을 직접 정해야 함

---

## 2. 상환 방식별 계산 정책 분리

### 문제
원리금균등과 원금균등은 월별 원금과 이자 계산식이 다릅니다. 하나의 함수에서 조건문을 계속 늘리면 새로운 상환 방식이 추가될수록 핵심 서비스가 복잡해집니다.

### 선택
공통 계산 인터페이스를 두고 상환 방식별 계산기를 분리합니다. 시뮬레이션 서비스는 어떤 계산기를 선택할지만 담당하고 실제 계산식은 각 계산기가 책임집니다.

### 이유
서비스 흐름과 금융 계산 정책의 변경 이유를 분리하기 위해서입니다.

---

## 3. 데이터 수집과 사용자 웹 요청 분리

### 문제
웹 요청은 짧은 응답시간이 중요하지만 외부 사이트 수집은 네트워크 지연, 장애, 재시도가 발생할 수 있습니다.

### 검토한 대안
1. Next.js 요청 안에서 실시간 수집
2. Python으로 주기적으로 수집한 뒤 DB 적재
3. 별도 대기열과 작업 처리자 사용

### 선택
현재는 Python 데이터 수집 파이프라인을 웹 요청과 분리해 DB에 먼저 적재합니다.

### 왜 대기열을 먼저 넣지 않았는가
현재 규모에서는 별도 메시지 브로커의 운영 복잡도가 더 큽니다. 수집 대상과 빈도가 증가하고 재시도·일정 실행·수평 확장이 실제 요구가 되면 대기열을 검토합니다.

---

## 4. 애플리케이션 검증과 DB 제약조건을 함께 사용

### 문제
웹 입력을 검사하더라도 데이터 수집기나 직접 SQL 등 다른 경로에서 잘못된 값이 들어올 수 있습니다.

### 선택
- 금리와 기간 범위: `CHECK`
- 상품 중복: `UNIQUE(bank_name, product_name)`
- 주요 조회 조건: 인덱스

DB를 마지막 데이터 무결성 경계로 둡니다.

---

## 5. 처음부터 서비스를 잘게 나누지 않음

현재는 계산 기능을 하나의 애플리케이션 안에서 유지합니다. 웹 서비스와 데이터 수집은 실행 특성이 달라 분리했지만, 마이크로서비스 자체를 목표로 두지는 않았습니다.

서비스 분리는 다음 요구가 실제로 확인될 때 검토합니다.

- 계산 API의 독립 배포가 필요할 때
- 데이터 수집이 웹 서비스 성능에 영향을 줄 때
- 적재량 증가로 작업 처리자의 수평 확장이 필요할 때
- 별도 장애 격리가 필요할 때

## 6. 재시도 중복은 멱등성으로 처리

### 문제
금융상품 적재 요청이 네트워크 오류로 재시도되면 같은 작업이 두 번 실행될 수 있습니다.

### 선택
- 같은 논리적 요청: `Idempotency-Key`로 식별
- 같은 금융상품: DB 유일성 제약조건으로 최종 차단

```text
재시도 가능성
  ↓
중복 실행 가능성
  ↓
멱등성 키로 같은 요청 식별
  ↓
DB 유일성 제약조건으로 최종 무결성 보호
```

측정하지 않은 개선 수치를 README나 포트폴리오 성과로 사용하지 않습니다.

```text
기준 상태
→ 같은 부하
→ 한 가지 변경
→ 같은 부하로 재측정
→ p50 / p95 / 처리량 / 오류율 비교
→ 결과와 단점 해석
```

기술을 적용했다는 사실보다 실제 문제 해결에 기여했는지를 확인합니다.
